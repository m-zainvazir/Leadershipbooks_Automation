# Phase 2 — Shopify Flows

**Written:** 2026-09-12. **Parent:** [`00-master-plan.md`](00-master-plan.md) phase 2.
**Context that shapes everything here:** fulfilment is via **IngramSpark, entirely manual**, with no
API credentials available. Shopify almost certainly never sees a fulfilment or a carrier
`DELIVERED` event.

---

## 1. The design inverts — read this before building

The original design (handoff doc §6) had three flows in a clear hierarchy:

| | Original intent | Reality with manual IngramSpark |
|---|---|---|
| Flow 2 — carrier `DELIVERED` | **primary**, carries most orders | ❌ **impossible.** No tracking in Shopify, no event, ever |
| Flow 1 — manual `delivered-manual` tag | safety valve | the only *accurate* signal — but only if a human applies it |
| Flow 3 — time-based backstop | rarely fires | ⚠ **likely the path that actually carries most orders** |

**The uncomfortable question: does anyone actually know when a book arrives?** IngramSpark ships
direct to the reader. If nobody sees a delivery confirmation, `delivered-manual` never gets applied,
and Flow 1 fires for nobody. A trial that only starts when someone remembers to tag an order is a
trial that mostly doesn't start — and the customer paid.

**So build Flow 3 as the primary path and Flow 1 as an accelerator**, not the other way round.
Flow 1 still matters: when you *do* know a book landed, it starts the trial immediately instead of
making the reader wait out the timer.

### Which way to err on timing

Starting the clock **before** the book arrives is the harmful direction — the reader burns trial
days on a coach for a book they cannot read, then the trial ends around when the parcel lands.
Starting it late costs only delay.

IngramSpark print-on-demand is roughly 1–3 business days to print plus 3–10 to ship. **21 days from
order** is the safe backstop. Tighten it later once you have real delivery data; do not start there.

### One copy change this forces

The welcome email currently opens *"Your book has arrived — so your Book Coach AI is now live."*
On the Flow 3 path that claim may simply be **false**, and it invites "no it hasn't" replies.

Change it to something true on both paths:

> **Your Book Coach AI is now live.**

Same warmth, no claim you cannot back. `source` still records which path fired, so you can tell
them apart in reporting.

## 2. Flow 3 — time-based (BUILD FIRST)

**Shopify admin → Automations → Flow → Create workflow**

| | |
|---|---|
| **Trigger** | **Order created** — *not* "Order fulfilled". With manual IngramSpark, orders may never be marked fulfilled, and a trigger that never fires is worse than no flow. |
| **Action 1** | **Wait** — 21 days |
| **Condition** | order tags **do not contain** `coach-started` **AND** order contains product `10434147320122` |
| **Action 2** | Send HTTP Request (§4), `source: shopify_flow_backstop` |
| **Action 3** | Add order tag `coach-started` |

The condition sits **after** the wait so that an order tagged `delivered-manual` in the meantime —
which sets `coach-started` via Flow 1 — silently drops out here. That is the whole idempotency
mechanism on the Shopify side.

---

## 3. Flow 1 — manual tag accelerator

| | |
|---|---|
| **Trigger** | **Order tags added** |
| **Condition** | added tag is `delivered-manual` **AND** order tags do not contain `coach-started` **AND** order contains product `10434147320122` |
| **Action 1** | Send HTTP Request (§4), `source: shopify_flow_manual` |
| **Action 2** | Add order tag `coach-started` |

**The product condition is not optional.** Without it, tagging *any* order `delivered-manual` starts
a coach trial for a customer who bought an unrelated book. Harmless with one coach and actively
wrong with fifteen.

**Key on product ID `10434147320122`, not SKU.** The bundle currently has `sku: null`, and this
catalogue already has a duplicate-SKU problem (`Life Without Reservation` paperback and
`Life Without Reservation Study Guide` both carry `9781951648213`).

## 4. The HTTP Request action

| Field | Value |
|---|---|
| Method | `POST` |
| URL | `<GHL_TRIAL_WEBHOOK_URL>` |
| Header | `Content-Type: application/json` |

### Body template

```json
{
  "event": "book_delivered",
  "source": "shopify_flow_backstop",
  "email": "{{order.customer.email}}",
  "first_name": "{{order.customer.firstName}}",
  "last_name": "{{order.customer.lastName}}",
  "phone": "{{order.customer.phone}}",
  "shopify_order_id": "{{order.id}}",
  "shopify_order_number": "{{order.name}}",
  "delivered_at": "{{order.createdAt}}"
}
```

> ⚠ **Build every value from Flow's variable picker, never typed from this file.** The object graph
> differs per trigger, and a wrong path fails **silently with an empty field** — you get a contact
> with no email and no way to tell why. This template is a shape to aim at, not a spec.

**Three things to check in the picker:**

1. **`order.id` is a GID**, like `gid://shopify/Order/5432109876543`, not a bare number. Harmless —
   it is only stored for support — but do not expect it to match Shopify admin's numeric ID.
2. **Phone may be empty.** Try `order.customer.phone`, then `order.phone`, then
   `order.shippingAddress.phone`. Whichever is populated is the one worth sending, because a phone
   on the contact is what auto-links the reader's handset and skips activation entirely.
3. **`delivered_at` on the backstop path is the order date**, not a delivery date. It is
   reporting-only (`coach_trial_started` is what the workflow writes), so this is acceptable — but
   do not later build logic on it believing it means delivery.

### Flow's HTTP action gives no feedback beyond its run log

Check **the flow's run log** before assuming GHL is at fault. A 2xx there means GHL received it;
after that, the GHL workflow's Execution logs take over.

## 5. Flow 2 — carrier DELIVERED · DEFERRED INDEFINITELY

Requires Shopify Shipping (or any integration) writing tracking onto the order from a supported
carrier. With manual IngramSpark fulfilment there is no such data, so **this flow cannot work and
should not be built.**

Revisit only if fulfilment moves into Shopify with tracking. At that point: clone Flow 1, change the
trigger to *fulfillment event created* with status `DELIVERED`, and set
`source: shopify_flow_delivered`. It would then become the primary path and Flow 3's wait could
shorten considerably.

## 6. Testing

Flow 1 is the only one testable on demand — that is its other virtue.

1. Place a real order for the bundle (**$29.95**, product `10434147320122`)
2. Add the `delivered-manual` tag to the order by hand
3. Check the **Flow run log** — did the HTTP request return 2xx?
4. Check **GHL Execution logs** — did the workflow run the full branch?
5. Check the contact — `coach_status: trial`, tag `bookcoach-micheal-stickler-active`
6. `npm run subs -- --sync` then `--list` from `../../coach-router` — is the contact entitled?
7. **Add the tag a second time** → nothing should change (Shopify-side lock)
8. Text `+1 854 254 5009` from the phone on the order → coach replies with no activation code
9. Refund yourself

**Step 8 is the one that proves both systems are joined.** Everything before it only proves the
commercial layer talked to itself.

Flow 3 cannot be tested on demand — it proves itself 21 days later. **Check `source` on new contacts
daily for the first three weeks after launch**; it is the only signal telling you which path fired,
and the only way to notice one silently failing.
