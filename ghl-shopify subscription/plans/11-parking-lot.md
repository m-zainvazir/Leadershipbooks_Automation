### Duplicate DMARC record

> 🔺 **PROMOTED OUT OF THE PARKING LOT — 2026-09-24.** New information: this was downgraded on
> 2026-09-19 because *our* five emails moved to the verified Mailgun domain and pass DMARC. But
> **Shopify's order-confirmation email is a different sender on a different domain**, and on
> 2026-09-24 a real $0 test order (#4233) produced a confirmation that Shopify's timeline says it
> sent and the customer never received.
>
> Re-verified live the same day — the duplicate is still present, and SPF is a **hard fail**:
>
> ```
> _dmarc.leadershipbooks.com  "v=DMARC1; p=none"
> _dmarc.leadershipbooks.com  "v=DMARC1; p=none; rua=mailto:dmarc@leadershipbooks.com"
> leadershipbooks.com         "v=spf1 include:spf.protection.outlook.com -all"
> ```
>
> **If Shopify sends as `@leadershipbooks.com`, SPF hard-fails it** — Shopify's servers are not in
> `spf.protection.outlook.com`, and `-all` instructs receivers to reject rather than soften. With no
> valid DMARC policy to consult (duplicate records = no policy), it lands on the receiver's own
> spam heuristics.
>
> ⚠ **Unconfirmed:** Shopify may send from its own domain instead, which would make this irrelevant
> to that symptom. **Check Shopify → Settings → Notifications → sender email before acting.**
>
> 🚫 **The SPF record must still not be modified** — see the warning below. Adding Shopify to it
> would not fix alignment anyway.

*(Original entry:)*

`_dmarc.leadershipbooks.com` returns **two** TXT records:

```
v=DMARC1; p=none; rua=mailto:dmarc@leadershipbooks.com   ← keep
v=DMARC1; p=none                                          ← delete
```

Per RFC 7489 a domain with multiple DMARC records is treated as having **no policy at all**, so the
`rua=` address collects nothing and there is no delivery reporting.

**Downgraded from launch blocker on 2026-09-19** — moving all sending to the verified dedicated
domain achieved `DMARC: PASS` without it. Still worth fixing for the reporting alone.

### Mailgun DKIM key for `leadershipbooks.com`

Only needed if sending from the brand domain (`@leadershipbooks.com`) is wanted again. GHL →
Settings → Email Services → Dedicated Sending Domain issues the records.

🚫 **Whoever does either must not modify the existing SPF record.**
`v=spf1 include:spf.protection.outlook.com -all` is what makes normal Microsoft 365 mail work, and
adding `include:mailgun.org` **would not fix alignment anyway** — SPF alignment is judged on the
Return-Path domain, which stays Mailgun's.
